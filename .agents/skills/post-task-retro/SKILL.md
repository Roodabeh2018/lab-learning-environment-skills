# Post-task retro

Turn a completed task into a concise learning note. Do not turn it into a transcript or stakeholder status report.

## Steps

1. Confirm the work is complete or deliberately paused. If it is still in progress, ask whether the user wants a midpoint note or would rather finish first. Do not describe unfinished work as done.
2. Name the concrete outcome, including the relevant artifact, decision, or behavior.
3. State how completion was checked: a test, command, screenshot, acceptance criterion, or other evidence. If no check was provided, say so instead of inventing one.
4. Identify one specific thing that worked and one specific risk, mistake, or near miss. If there was no meaningful risk, say that briefly.
5. Turn the learning into one reusable rule for similar work.
6. Keep the result to four short sections; for a tiny task, use four concise lines.

## Output

### Outcome
- Finished:
- Verified by:

### What I learned
- Worked:
- Risk or near miss:
- Reusable rule:

## Boundaries

- Do not invent outcomes, verification, mistakes, or lessons.
- Do not reproduce the whole conversation.
- Do not create or save a learning-log file unless the user asks.
- For an unresolved concrete failure, use an error diagnosis; for several notes across a week, use a weekly review.
